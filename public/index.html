Project Name

Giving your software a clear and memorable name turns a random idea in your head into a real, concrete project. Instead of calling your work "new-test-app" or "project-final-2", a real name gives your system an identity that people can recognize and talk about. Having a proper name also helps you organize the practical side of programming from day one. You will use this name to create your GitHub repository, name your local folders, and label your documentation files so everything stays connected in one place. In addition, a good project name makes your portfolio look much more professional. When you show your work to recruiters, classmates, or clients, presenting a named product shows that you treated the code with care and structure from the very beginning.

  • - You always know why a feature is important before writing any code.
  • - Prevents you from wasting weeks building tools that nobody actually needs.
  • - Keeps you motivated
  • - Remembering the real frustration that started the project helps you keep going when you hit hard bugs.
  • - Connects your daily coding effort to a clear, meaningful purpose.
  • - Explains the context to others
  • - Anyone opening your repository immediately understands why this project exists.

Project Objective

  • - Explains your main goal in one simple, direct sentence so anyone reading your docs understands it right away.
  • - Works as a filter against distractions
  • - If a new idea does not directly help this objective, do not build it right now.
  • - Keeps your focus sharp when you feel tempted to add random features.
  • - Defines what "finished" looks like
  • - Gives you a clear finish line so you know when the project reached its main goal.
  • - Helps you and your teammates agree on what the software must deliver.

Target Audience

Knowing exactly who will use your software changes almost every design and code choice you make. You do not build a tool for experienced programmers the same way you build an app for store owners, students, or everyday users. For example, a tool made for developers can use terminal commands, keyboard shortcuts, and Markdown files without any problem. On the other hand, an app made for non-technical users needs big, clear buttons, visual hints, and simple words with zero technical jargon. Writing down your target audience also keeps you honest during development. Whenever you design a new screen or button, you can ask yourself: "Would my target user understand how to use this without my help?"

Solution Proposal

  • 2. Gives you a quick 30-second explanation ready whenever someone asks what you are building.
  • 3. Connects the user's problem directly to how your app works in practice.
  • - Shows the main steps of how the user interacts with your tool.
  • - Summarizes the core idea before diving into complex code details.
  • 4. Helps align everyone on the team around the same big-picture solution before coding starts.

Differentiators

  • - Shows you researched similar tools first instead of blindly copying what already exists.

  • - Highlights your unique value

  • - Looks great in job interviews when explaining your technical choices.

Initial Tech Stack

Choosing your programming languages, frameworks, and storage tools early stops one of the most common beginner mistakes: switching technologies in the middle of the project just because you watched a new video or tutorial online. When you lock in a simple, clear stack from the beginning - like Node.js, HTML, CSS, and local files - you spend your energy solving the real problem instead of constantly relearning basic syntax or setting up new environments. Documenting your tech stack also helps anyone who downloads your project later. They can immediately see what tools they need installed on their computer to run and test your code without guessing.

MVP Objective

MVP stands for "Minimum Viable Product." Instead of spending an entire year trying to build a giant, perfect app that never gets finished, the MVP objective defines the smallest working version you can build and test quickly. Think of the MVP as the basic core of your software with zero extra decoration. It does not need fancy animations, complex user profiles, or twenty different themes - it just needs to solve the main problem from start to finish. Finishing a simple first version teaches you much more than planning a huge system forever. Once your MVP works, you have a real, functional project in your hands that you can improve step by step.

Project Initialization

  • - Defines the very first setup actions that prepare your project folder to work properly.
  • - Automatic folder and file creation
  • - Creates the base /docs folder and generates the 6 standard Markdown templates.
  • - Generates the project.yaml metadata file to store basic project info.
  • - Gives beginners a ready-to-use structure from the first second without manual setup.

  • - Turns vague ideas into simple actions like creating folders, listing files, and saving text.
  • - Makes it much easier to estimate how long each part will take to code.
  • - Protects your focus during development
  • - Gives you a clear checklist so you know exactly what must be built first.
  • - Helps you avoid spending hours on minor details before the core system even works.

Out of Scope (What NOT to build now)

  • - Every programmer gets flooded with cool ideas during a project - like login screens, dark mode, AI tools, or cloud sync.
  • - Stops extra features from ruining your deadline
  • - Breaks the bad habit of saying "just one more small feature", which leaves most beginner projects unfinished.
  • - Creates a clear boundary so you stay loyal to your MVP plan.
  • - Saves good ideas for later
  • - You are not throwing creative ideas away - you are just parking them safely until version 1.0 works.

Requirements Objective

While the scope shows the big picture of your project, requirements turn those general ideas into clear, specific technical rules. This document acts like a rulebook that explains exactly what the system must do and how it must behave. Having clear requirements removes guesswork when you sit down to code. Instead of wondering "how should this button work?", you can check your requirements list and follow the exact behavior you already planned. Think of this file as a checklist contract for your software: when every rule written here works properly in your code, your MVP is officially complete and ready to use.

Functional Requirements (FR)

  • - Describes every concrete action, button, or task the software must perform.
  • - Connects almost directly to your code
  • - Each requirement usually becomes a specific function, a button click, or a server route.
  • - Examples include creating default files, listing documents, editing text, and saving changes.
  • - Makes testing simple and objective
  • - You can easily test each requirement one by one to check if it works or fails.
  • - Helps you spot broken features before anyone else uses your app.

Non-Functional Requirements (NFR)

  • - Non-functional requirements are not about what buttons exist, but how well the software works behind the scenes.
  • - Sets technical limits and environment rules
  • - Defines whether the app must run offline without internet access.
  • - Specifies if the system avoids heavy databases and works on Windows, Linux, and macOS.
  • - Protects speed and simplicity
  • - Ensures the interface responds fast when clicking buttons or saving files.
  • - Keeps installation easy enough that beginners do not give up before the app even starts.

Data & Storage Rules

Every application needs clear rules about how information is saved and kept safe. Instead of setting up complex SQL databases right away, simple projects often save data directly inside local text files like Markdown and YAML. Defining these storage rules early prevents messy bugs later. You decide exactly where files live, how edits overwrite old content safely, and how metadata like project status and creation date stay structured. When storage rules are clear and simple, backing up or moving your project to another computer is as easy as copying a single folder.

Testing & Validation

  • 1. Uses your requirements list as a final verification checklist before calling a feature finished.
  • 2. Checks both normal actions and edge cases
  • - What happens when a document is completely empty?
  • - Does the progress bar update right away after saving new text?
  • 3. Gives you confidence that your software works reliably for real users.

Development Model

A development model defines the routine and structure you use to build your software over time. Without a simple method, it is very easy to jump randomly from file to file, leave half-finished code everywhere, and lose track of what you were doing. For solo developers and small student projects, you do not need heavy corporate meetings or complicated rules. Using a lightweight approach - like a personal Kanban board with incremental deliveries - keeps your workflow realistic and stress-free. The goal of choosing a development model is to match your coding routine to your real schedule, helping you make steady, consistent progress every week without burning out.

Work Organization (Columns/States)

  • - Splits your work into three clear visual states so you always know what is happening.
  • - To Do (Waiting in line)
  • - Holds tasks that are already planned, keeping your mind free from worrying about future work today.
  • - Doing (In progress right now)
  • - Holds only the one or two tasks you are coding at this exact moment, stopping you from starting five things at once.
  • - Done (Finished and tested)
  • - Collects completed tasks, giving you visible proof of how much progress you have made.

Source of Organization

Putting tasks on sticky notes, phone reminders, browser tabs, and random text files is one of the fastest ways to forget important bugs and lose control of your project. Choosing one central file - such as 06-backlog.md inside your own repository - as your single source of truth ensures you always know exactly where to look when you sit down to code. Because the task list lives right next to your code, you can update your tasks and commit your changes together, keeping your project history clean and organized in one place.

Development Workflow

  • 1. Builds a clean, repeatable habit for creating every feature from start to finish.
  • 2. Follow the same simple loop for every task
  • - Pick one small task from the backlog and move it to Doing.
  • - Write the code and test it locally to make sure nothing broke.
  • - Update your documentation if needed, then move the task to Done.
  • 3. Helps you build strong professional discipline early in your programming career.

Approach and Principles

  • - Build the MVP first
  • - Focus on making the core features work from start to finish before adding visual polish.
  • - Grow step by step
  • - Improve the software in small, safe increments instead of rewriting everything at once.
  • - Working code before perfect code
  • - Make the code work cleanly first; optimize and refactor it later once you understand the problem better.
  • - Avoid unnecessary complexity early on so you keep moving forward.

Evolution Control

Once your first version is working, you will naturally want to add new capabilities and improvements. However, adding dozens of random updates at the same time can quickly break what already works. Grouping future improvements into clear, organized phases - almost like "seasons" of a TV show - keeps your project growing safely. Each phase focuses on a specific group of features that make sense together. By finishing one phase completely before starting the next, you keep your codebase stable, your documentation accurate, and your progress easy to track over the long term.

System Overview

The System Overview is like the floor plan of a house before you start raising the walls. It gives any developer a clear, high-level view of the main parts that make up the application and how they connect. For example, a local web tool can be broken down into three simple pieces: a browser screen for the user, a local Node.js server handling the logic, and local Markdown files storing the data. In less than thirty seconds, anyone opening your repository can read this overview and immediately understand how the entire machine fits together without reading hundreds of lines of code first.

Layered Architecture

  • - Separates your code by responsibility so each part has one clear job.
  • - Frontend (Screen & Interface)
  • - Handles everything the user sees and clicks in the browser, keeping visual code separate from file operations.
  • - Backend (Local Server & Logic)
  • - Works as the middleman that reads files, calculates progress, and safely processes requests from the screen.
  • - Filesystem (Data Storage)
  • - Saves all text and metadata directly inside .md and .yaml files without needing a complex database.

Data Flow

Understanding how data moves through your software makes full-stack programming much less mysterious for beginners. Data flow traces the exact journey of information from a user's action until the screen updates. For example: the user clicks "Save" in the browser, the frontend sends a request to the local API, the backend writes the new text into the Markdown file on disk, and then sends a confirmation back to update the dashboard. When a bug happens, knowing this path makes fixing it ten times easier because you can check each step of the journey until you find where the data stopped.

Folder Structure

  • - Maps out where every file and folder lives before you start creating them randomly in your editor.
  • - Keeps different parts of the project cleanly separated
  • - Screen files (HTML, CSS, JS) stay organized inside /public.
  • - Server routes and logic stay grouped inside /server.
  • - Project documentation lives neatly inside /docs.
  • - Makes your repository look clean, predictable, and professional from day one.

Architectural Decisions

  • 1. Every software project requires technical choices - such as using local Markdown files instead of setting up PostgreSQL or MongoDB.
  • 2. Prevents doubt and confusion later
  • - Writing down why you made a choice stops your future self from looking at the code six months later and wondering what you were thinking.
  • - Explains the trade-offs between simplicity, speed, and project size.
  • 3. Helps new contributors understand and respect the design boundaries of your project.

Future Evolution

  • - Lists potential technical upgrades that the system can support later without throwing away your current code.
  • - Examples of future growth
  • - Supporting multiple projects at the same time instead of just one folder.
  • - Adding local network sharing for small teams or an optional database if the project scales up.
  • - Encourages you to write clean, modular functions today so adding bigger features tomorrow is painless.

Backlog Objective

Opening an empty code editor without a concrete task list often causes instant creative freeze - you stare at the screen and do not know where to begin. The backlog solves this by turning all your planning into an actionable to-do list. Here, big ideas from your vision, scope, and architecture are broken down into small, specific coding steps ordered by priority. Instead of "build the whole app", you get clear tasks like "create GET /docs route". Having a clear backlog means every time you open your computer to code, you already know the exact next step to take without wasting time deciding what to do.

Task Blocks by Area

  • - Groups similar coding tasks into clear, logical categories so you work with focus.
  • - Common project blocks
  • - Project Setup & Backend Base: creating folders, package.json, and basic server routes.
  • - Filesystem & Editor: reading, editing, and saving Markdown files safely.
  • - Dashboard & Progress: displaying file statuses and overall completion bars.
  • - Lets you finish and test one technical layer completely before jumping to the next.

Living Kanban Board

Unlike earlier documents such as the Project Vision - which stay mostly the same once you write them - your backlog is a living workspace that changes every single day you write code. Each task moves across your board from To Do, into Doing while you work on it, and finally lands in Done once it is tested and working properly. Watching completed tasks pile up in the Done column gives you real, visible proof of your progress and keeps your energy high until the entire MVP is finished.

Task Priority & Order

  • - Organizes tasks from top to bottom so you always build the foundation before the roof.
  • - Follows a natural technical sequence
  • - Start with folder structure and server setup before building visual screens.
  • - Connect file reading and saving before adding progress bars or extra polish.
  • - Stops you from getting stuck on features that depend on code you have not written yet.

Update Rules

  • 1. Treat the backlog as an active checklist that grows and changes alongside your code.
  • 2. Keep the list honest every day
  • - Whenever you discover a new bug or hidden task while coding, write it down in To Do right away instead of relying on memory.
  • - Move tasks to Done immediately after testing them so the file always reflects reality.
  • 3. Never let the backlog go stale - an outdated task list quickly stops being useful for controlling your project.
